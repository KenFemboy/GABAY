GABAY - Known limitations and follow-ups
=========================================
Stages 3 to 11. Last updated 2026-11-28.

This file is a to-do list for later. Each item says what the limit is and, where there is one,
what to do about it. Update the file when an item is fixed or a new limit is found.


-------------------------------------------------------------------------------
STAGE 3 - LEARNER RECORDS
-------------------------------------------------------------------------------

Not yet confirmed or checked
- The learner fields were chosen during development and still need to be confirmed with the
  SNED Coordinator. They are: learner_code, first/middle/last name, birth_date, sex,
  grade_level, section, school_year, status.
- The screens have not been clicked through in a browser for each role (Coordinator, Teacher,
  School Head, System Admin). Only the automated tests have been run.

Access rules (as designed; review them if school policy changes)
- Teachers see a learner only while they are assigned to that learner for the learner's CURRENT
  school_year. When a learner's school_year changes, the old teacher loses access until they are
  assigned again for the new year, so assignments have to be redone every school year.
- A Teacher who opens a learner they are not assigned to gets 404 (not found), not 403. This is
  on purpose, so record IDs cannot be probed.
- The System Administrator has no access to learner data at all.
- Teachers cannot edit learner fields. Only the SNED Coordinator can.
- Learners are never deleted. There is no DELETE endpoint; change the status instead (active,
  transferred, graduated or inactive).
- Deactivating a Teacher account does not remove their assignments. They cannot sign in, so they
  cannot see anything, but the assignment rows stay.

Validation limits
- learner_code is a free-form school code: letters, digits and "-", up to 32 characters, stored
  in upper case. It is NOT checked as a DepEd LRN.
- school_year only has to look like "2025-2026" (the second year must be the first year + 1). Any
  year range that fits this pattern is accepted, for example "1900-1901".
- birth_date cannot be in the future and must be within the last 30 years. The 30-year check
  compares years only.
- The grade levels are a fixed list: K, 1-12 and NG (non-graded).
- Sex can only be male or female.
- The section filter on the learner list needs the exact section name (upper or lower case does
  not matter). It does not match part of a name.

Performance and scale
- Learner search uses LIKE '%text%', which cannot use a database index. This is fine at school
  size. For very large data, add a pg_trgm index or full-text search.
- The teacher dropdown (GET /api/users/teachers) loads every active Teacher at once, with no
  paging.

Other
- The frontend guesses the current school year by assuming it starts in June (see
  currentSchoolYear in Frontend/src/features/learners/constants.js).
- The seed script (python -m app.scripts.seed_learners) refuses to run only when ENVIRONMENT is
  exactly "production". It creates fake learners only. Never load real learner data into
  development.
- A missing field now gives the message "This field is required." on EVERY endpoint, including
  users, not only on learner endpoints.
- AUDIT LOGGING IS NOT DONE YET (planned for Stage 14). Nothing records who viewed or edited a
  learner. Add it in learner_service.get_visible_learner and learner_service.update_learner.


-------------------------------------------------------------------------------
STAGE 4 - ASSESSMENTS AND DOCUMENT UPLOAD
-------------------------------------------------------------------------------

Not yet confirmed or checked
- Supabase Storage has only been tested against a MOCKED Supabase (tests/test_storage.py), never
  against the real project. Before relying on it:
    1. Create the private bucket "gabay-documents".
    2. Set STORAGE_BACKEND=supabase, SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY in Backend/.env.
    3. Upload a file and check that it appears under assessments/.
    4. Check that preview (iframe) and download both work with the signed URL.
    5. Check that the signed URL stops working after 60 seconds.
- The screens (upload with progress bar, preview, download, remove, status buttons) have not
  been clicked through in a browser.
- Production storage is Supabase Storage, chosen instead of S3 or GCS. A different provider
  needs a new class in app/services/storage_service.py that implements StorageBackend.

Upload limits
- FastAPI receives the WHOLE upload before GABAY's size check runs. Oversized files are rejected
  and never stored, but the server still receives them. For production, also set a request size
  limit on the reverse proxy (for example nginx client_max_body_size 16m) and the Supabase
  bucket's file size limit.
- Each upload is held in memory (up to MAX_UPLOAD_MB, default 15 MB) while it is checked.
- The 15 MB limit is set in TWO places:
    Backend:  MAX_UPLOAD_MB in .env (app/core/config.py)
    Frontend: MAX_UPLOAD_MB in Frontend/src/features/assessments/constants.js
  If you change one, change the other.
- The file type check looks only at the first bytes of the file (the "magic bytes"). Any file
  that starts with "%PDF-" passes as a PDF. Files are not virus-scanned and PDFs are not checked
  further or cleaned. If needed later, add antivirus scanning (for example ClamAV) or PDF
  sanitising.
- Only PDF, JPG/JPEG and PNG are accepted. HEIC photos taken on phones, Word files and similar
  are rejected.

Duplicates
- A duplicate is detected per learner, and only when the bytes are exactly the same (same
  SHA-256). If the same paper is scanned again, the bytes differ and it is NOT treated as a
  duplicate.
- The same file can be uploaded for a different learner.

Workflow limits
- Each assessment has one document. To replace it, the Coordinator removes the current document
  and then a new one is uploaded.
- Only the SNED Coordinator can remove a document. A Teacher who uploaded the wrong file has to
  ask the Coordinator.
- Removing a document sets the assessment back to Draft. Documents cannot be removed while the
  assessment is Processing or once it is Finalized.
- Status transitions are defined in one place, app/services/assessment_status.py:
    Automatic: Draft -> Uploaded (upload), Uploaded/Processed/Needs Review -> Draft (remove),
               Uploaded/Processed/Needs Review -> Processing (POST /process),
               Processing -> Processed or Needs Review (OCR finished),
               Processing -> Uploaded (OCR failed completely)
    Manual:    Processed -> Needs Review or Finalized; Needs Review -> Finalized;
               Finalized -> Needs Review (reopen)
  Only the SNED Coordinator can make manual changes (PATCH /api/assessments/{id}/status).
  Teachers cannot flag an assessment for review.
- Later stages (extraction etc.) must change status through
  assessment_status.transition(..., manual=False), never by setting processing_status directly.
- Status changes are not recorded anywhere. There is no history of who finalized or reopened an
  assessment (see AUDIT LOGGING below).
- Assessment details (type, date, assessor, notes) cannot be edited yet, and an assessment
  record cannot be deleted.

Signed URLs
- Anyone who has a signed URL can open the file until it expires (SIGNED_URL_TTL_SECONDS,
  default 60). A link can be used more than once until it expires.
- Local storage: the token in the URL is the only permission, and the /api/files/{token} route
  does not check who is signed in. The tokens are signed with JWT_SECRET_KEY, so changing that
  key cancels any links that are still open.
- PUBLIC_API_URL must be the address the BROWSER uses to reach the API. If it is wrong, local
  preview and download links break.
- Supabase: the download link adds ?download=<filename>. The iframe preview depends on Supabase
  allowing its files to be shown inside a frame. Check this in step 4 of "Not yet confirmed"
  above.

Keeping the database and storage in step (rare edge cases)
- Upload: if the database commit fails AND the cleanup delete in storage also fails, a stray file
  is left in storage. It is logged as "Could not remove orphaned object ...".
- Remove: if the storage delete succeeds but the final database commit then fails, the database
  row still points to a file that no longer exists. This is very unlikely.
- The database deletes a learner's assessments and documents automatically if the learner is
  deleted (ON DELETE CASCADE), but that would leave their files in storage. Learners are never
  deleted, so this should not happen. If learner deletion is ever added, delete the files from
  storage first.

Configuration and security
- SUPABASE_SERVICE_ROLE_KEY bypasses all of Supabase's access rules (RLS). Keep it in
  Backend/.env only. Never put it in Frontend/.env or commit it.
- STORAGE_LOCAL_DIR defaults to the relative path "storage", which is resolved from the folder
  the server is started in. Start uvicorn from Backend/, or set an absolute path.
- The learner profile only counts assessments in its summary if app/services/assessment_service.py
  has been imported. The API always imports it (through the assessments router), but a
  standalone script may not.
- AUDIT LOGGING IS NOT DONE YET (planned for Stage 14). Nothing records uploads, downloads or
  removals. Add it in assessment_service: get_visible_assessment, upload_document,
  delete_document, change_status and document_signed_url.

STAGE 5 - OCR PROCESSING
-------------------------------------------------------------------------------

Not yet confirmed or checked
- Tesseract is NOT installed on the development machine yet. Every OCR test except one uses a
  fake OCR engine. The real-Tesseract test (tests/test_ocr.py::test_real_tesseract_reads_rendered_text)
  is skipped until Tesseract is installed. After installing it, run the tests again and check
  that /api/config/status shows "ocr_available": true.
- OCR quality has not been checked on real (synthetic but realistic) SNED assessment forms,
  handwritten notes, or phone photos. Test this before relying on the confidence threshold.
- The Dockerfile has not been built or run.
- The review screen has not been clicked through in a browser.

Running it
- The OCR worker is a SEPARATE process: python -m app.workers.ocr_worker (run from Backend/).
  If it is not running, jobs stay "queued" and assessments stay in Processing forever. The UI
  does not detect that the worker is missing.
- If the worker is killed in the middle of a job, the job is picked up again after
  OCR_JOB_TIMEOUT_MINUTES (default 30). After OCR_MAX_ATTEMPTS (default 2) tries, it is marked
  failed and the assessment returns to Uploaded.
- Each worker processes one job at a time. To process more at once, run more workers; they
  share the queue safely through FOR UPDATE SKIP LOCKED (PostgreSQL).
- If Tesseract or a language (eng, fil) is missing, the worker still starts, but every job fails
  with a message saying what is missing.

Accuracy and limits
- Tesseract is poor at handwriting. Handwritten pages will usually get low confidence and
  go to Needs Review, and the text may be unusable.
- The Filipino (fil) model is less accurate than English. Mixed eng+fil OCR is also slower.
- Confidence is Tesseract's own word confidence (mean, weighted by word length). It is a
  rough signal only. A page can score high and still have wrong words.
- Confidence only rates the words Tesseract FOUND, not the ones it missed. On a very faded
  page, Tesseract may read only the large header and skip the body, and the page still
  scores 80-85% and can go straight to Processed. Seen while making the sample documents
  (app/scripts/make_ocr_samples.py). Possible fix later: also flag pages whose word count is
  much lower than the other pages, or lower than expected for the page size.
- An assessment goes to Needs Review if ANY page failed or ANY OCR page is below
  OCR_REVIEW_CONFIDENCE (default 70). Text-layer PDF pages are not scored and are trusted
  as they are, even if the PDF's embedded text is wrong.
- A PDF page counts as having a text layer when it has at least OCR_MIN_TEXT_LAYER_CHARS (20)
  characters. A page with a short caption over a scanned image will use the caption and skip
  OCR. Lower or raise the setting if this happens.
- Only the first OCR_MAX_PAGES (default 50) pages are processed. Later pages are recorded as
  failed ("Page limit reached").
- Each page has a time limit of OCR_PAGE_TIMEOUT_SECONDS (default 120).
- Pages are not deskewed or de-rotated (other than the EXIF rotation on photos). Crooked
  scans OCR worse. The preprocessing is grayscale, resize, auto-contrast and a light noise
  filter only.
- Encrypted (password-protected) PDFs cannot be processed.

Review workflow
- Reprocessing (allowed from Processed or Needs Review) REPLACES all OCR pages. Any
  corrections made in the review screen are lost. The UI asks for confirmation first.
- Corrections are allowed only while the assessment is Processed or Needs Review. Finalize
  locks them; reopen (Finalized -> Needs Review) to edit again.
- Saving a correction does not change the status. The Coordinator decides when to finalize.
- There is no edit history. Only the latest correction, who made it and when, are kept.
- The PDF page shown next to the text uses the browser's PDF viewer (#page=N). Some browsers
  ignore #page and always show page 1.
- Removing the document deletes its OCR pages and jobs (ON DELETE CASCADE), including any
  error message from a failed job.

Security and privacy
- OCR text is learner data. It is stored in PostgreSQL in plain text, like other learner
  fields, and is protected only by database access controls. It is never written to logs.
- The worker needs the same DATABASE_URL and storage settings as the API (including
  SUPABASE_SERVICE_ROLE_KEY when using Supabase).
- AUDIT LOGGING IS NOT DONE YET (Stage 14). Nothing records who started processing or who
  corrected the text, beyond reviewed_by on each page.

STAGE 6 - INFORMATION EXTRACTION AND REVIEW
-------------------------------------------------------------------------------

Not yet done
- OPTIONAL AI EXTRACTION IS NOT BUILT (the Stage 6 checklist item stays open). There is no
  de-identification step either. To add it later:
    1. Write an extractor class in app/services/extraction/ that follows the Extractor
       interface (base.py) and returns an ExtractionResult (schema.py).
    2. Replace the learner's name, code, birth date and other identifiers in the page text
       before sending it, and map the source quotes back to page offsets by searching
       for them in the original text.
    3. Hook it up in registry.py behind EXTRACTION_AI_ENABLED.
  The database already accepts method = 'ai'.
- The Analysis page has not been clicked through in a browser.
- The rules have only been tested on the synthetic sample reports (make_ocr_samples.py).
  Real DepEd / psychologist report layouts may differ. Collect a few anonymised examples and
  tune the heading and cue lists in rules.py.

How the rules can go wrong
- The rules depend on headings. A report with no headings, or headings the keyword list does
  not know, gives few or no findings. Unknown sections (for example "Reason for referral",
  "Tests administered") are skipped on purpose.
- Strengths and needs inside domain sections are found with cue words ("difficulty",
  "able to", "nahihirapan", "masigla", ...). This is a heuristic:
    - A sentence with both kinds of cue counts as a need ("Works well in pairs but becomes
      restless" -> need).
    - Sentences with no cue word only appear inside the present-level finding.
    - Negations are not understood ("does not have difficulty" -> need).
- The same sentence can appear both in a present level and as a strength or need. That is
  intended.
- Sentences are split at ". " followed by a capital letter, so abbreviations like "Dr. Cruz"
  can split a sentence.
- The domain of a finding outside a domain section is guessed from keywords and can be wrong
  or empty. Reviewers should check it.
- A diagnosis is ONLY taken from an explicitly labelled line (Diagnosis, Diagnostic/Clinical
  impression, Classification). The rules never infer one.
- The English and Filipino cue lists are short. Other languages are not supported.

Versions and approval
- Extraction runs only on Finalized assessments, and only one draft can be open per
  assessment.
- If an assessment is reopened and its OCR text changes, every version is flagged
  "source changed" (stale): drafts cannot be approved, and the page references may point at
  the wrong text. The previously APPROVED findings stay available to goal matching, marked
  "stale": true in GET /api/learners/{id}/findings. The Coordinator should run extraction again
  and approve the new version.
- Approved and superseded versions are never deleted. Removing the document or deleting the
  assessment deletes its versions (ON DELETE CASCADE).
- Only the SNED Coordinator can approve. Teachers can run extraction and edit drafts.
- AUDIT LOGGING IS NOT DONE YET (Stage 14). Beyond created_by and approved_by on each
  version, nothing records who edited which finding.

STAGE 7 - GOAL BANK
-------------------------------------------------------------------------------

Not yet confirmed or checked (two checklist items are only half done)
- "Domains and skills agreed with the SNED Coordinator": NOT DONE. The 9 domains and 30 skills
  in app/data/goal_bank_seed.json are a proposal from the development team. The Coordinator
  should review them in Goal bank -> Domains & skills (rename, add, deactivate).
- "Starter set of reviewed, measurable goals": the 50 goals are written to be measurable
  (condition + behavior + numeric criterion), but NOBODY HAS REVIEWED THEM YET. They load as
  Draft. They become usable for matching only when the Coordinator activates them one by one.
- The Goal bank screens have not been clicked through in a browser.
- The Docker image has not been built with the embedding model.

Embeddings
- The model (sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2, about 240 MB) is
  downloaded from Hugging Face the first time it is used, so the server needs internet once.
  After that it works offline from EMBEDDING_CACHE_DIR (default Backend/.models, gitignored).
  In Docker, mount a volume at /app/.models, or the model is downloaded again in every new
  container.
- The first Reindex, search or worker run after a restart loads the model, which takes a few
  seconds and about 300-500 MB of RAM in each process that uses it (the API process for
  Reindex and Find similar, and the worker process).
- Quality: English findings match the right goals well in testing. Filipino text matches
  noticeably more weakly (similarity around 0.35-0.40 against the English goals). Writing goal
  statements in both languages, or a larger model, would help. Similarity is a suggestion
  only; a person always chooses the goals (Stage 8).
- Similarity is computed in Python over all active goal vectors. That is fine for a few
  thousand goals. For much larger banks, move the vectors to pgvector.
- Changing EMBEDDING_MODEL makes the next reindex replace every vector, and vectors from the
  old model are deleted.
- The worker only re-indexes automatically while it is running (about once a minute). Without
  the worker, use the Reindex button or python -m app.scripts.reindex_goals.

Versioning and status
- A version counts as "used" only when later stages call goal_service.record_goal_usage().
  Nothing calls it yet (the IEP stage will). Until then, every edit happens in place.
- Archived goals cannot be edited. Activate one first, edit it, then archive it again if
  needed.
- Only unused Draft goals can be deleted. Domains and skills are never deleted, only
  deactivated. A skill that goals use cannot be moved to another domain.
- Domain codes cannot be changed, because extraction findings use the same codes.
- There is no CSV import or export for goals yet.
- AUDIT LOGGING IS NOT DONE YET (Stage 14). Each version records who created it, but nothing
  records who activated or archived a goal.
- (Stage 8) Goal vectors moved from bytes to a pgvector column in migration 0008. Find similar
  now uses the same pgvector search as matching.

STAGE 8 - SEMANTIC GOAL MATCHING
-------------------------------------------------------------------------------

Not yet confirmed or checked
- PGVECTOR IS NOT INSTALLED YET on the development database (PostgreSQL 18 on Windows), so
  migration 0008 has NOT been run against PostgreSQL, and the pgvector SQL search has not run
  on a real database. Install it (README: "Install pgvector"), then run "alembic upgrade head".
  The optional test tests/test_matching.py::test_pgvector_search_matches_numpy checks that the
  SQL search returns the same results as the numpy search. It runs only when TEST_PG_URL points
  to a THROWAWAY database, because it drops and recreates every table there.
- The prebuilt Windows pgvector (andreiramani/pgvector_pgsql_windows) is a community build, not
  made by the pgvector project. For production, prefer Linux/Docker (pgvector/pgvector image)
  or a managed Postgres with pgvector.
- The Goal suggestions page has not been clicked through in a browser.

Benchmark and accuracy
- The benchmark (app/data/matching_benchmark.json, 68 needs) is SYNTHETIC and was written by
  the developer, who also wrote the starter goals. It probably overstates real accuracy. The
  SNED Coordinator should review it and add real, anonymised needs.
- With the domain filter on, a need only competes with the goals of one domain and grade band
  (median 6), so top-5 accuracy is high even for random ordering (82%). The "domain filter
  off" numbers (97% versus 15% for random) better show what the model adds.
- Filipino-only needs match worst (80% top-5). Both misses were Filipino ("magbawas",
  "mainip").
- MATCH_MIN_SCORE (0.35) and MATCH_TOP_K (5) were chosen on the synthetic benchmark only.
- If a finding has the wrong domain (Stage 6 guesses domains), the domain filter hides the
  right goals. Switch the filter off for that run, or fix the domain in a new extraction
  version.
- Similarity is only a suggestion. Nothing is added to a learner without a person accepting
  it.

Behaviour to know
- Only approved NEED findings are matched. Strengths, present levels and recommendations are
  not.
- Matching only sees ACTIVE goals. Draft starter goals are invisible until the Coordinator
  activates them.
- Each run saves new suggestion rows. Earlier accept and reject decisions (and edited wording)
  are copied into the new run for the same need and goal version. "Selected goals" = accepted
  suggestions of the LATEST run + accepted manual additions. Older runs are kept as history.
- Accepting a goal records a goal-bank usage (goal_usages), which permanently locks that goal
  version: later edits in the goal bank create a new version (Stage 7 rule). Undo does not
  remove the usage.
- Edited wording (statement, target, criterion) is stored on the recommendation for this
  learner only. The goal bank is not changed.
- If the goal bank changes after a run (a goal archived or a new version), old suggestions
  still point at the version they were made for. Run matching again to see the current bank.
- A finding has only one domain, so a need that spans two domains (for example reading and
  behavior) matches in one of them only, unless the domain filter is switched off.
- The model runs inside the API process for matching runs and Find similar. The first run
  after a restart takes a few seconds to load it.
- AUDIT LOGGING IS NOT DONE YET (Stage 14). Each recommendation records who decided and when.
  Nothing else is logged.

STAGE 9 - IEP BUILDER
-------------------------------------------------------------------------------

Not yet confirmed or checked
- Migration 0009 has NOT been run on the development database yet. Run "alembic upgrade head"
  (it only creates the three new IEP tables).
- The DOCX layout is the developer's DepEd-style design, NOT an official DepEd or school form.
  The section names, the "Republic of the Philippines · Department of Education" header line
  and the signature block should be confirmed with the SNED Coordinator. The generated file has
  been checked by reading its text in the tests, but has not been opened and checked visually
  in Word.
- The IEP screens have not been clicked through in a browser.

Document
- DOCX only (no PDF). Staff can print or "Save as PDF" from Word or Google Docs.
- The document is generated each time it is downloaded and is not stored. A finalized IEP
  cannot change, so it always produces the same content, but the "Generated on" date in the
  footer changes.
- Signatures are printed lines only. There are no e-signatures and no record of who signed.
- Word fills in "Page X of Y" when the file is opened. Some viewers show "1" until the fields
  are updated.

Versioning and rules
- One IEP series per learner per school year (taken from the learner's CURRENT school year).
  For a new school year, change the learner's school year first, then create a new IEP.
- Only one draft per learner and school year. An amendment can be started only from the
  current finalized version.
- Superseded and finalized versions are never deleted. Discarding is allowed for drafts only.
- Findings and goals are copies. If extraction or the goal bank changes after an IEP is
  finalized, the IEP keeps its old text. Use an amendment and Re-import to bring in new items.
- Re-import adds only NEW approved findings and accepted goals. It does not remove items that
  were rejected later, and it does not update the text of items already in the IEP.
- Every goal taken from the goal bank or from an accepted suggestion records a goal-bank usage
  ("iep_goal"), which locks that goal version in the bank (Stage 7 rule).

Validation limits
- Validation checks that required fields are present and that dates are consistent. It does
  not judge quality (for example, whether a baseline is really measurable).
- Default dates assume a June–May school year (start = today or 1 June, end = 31 May, annual
  review two weeks before the end, quarterly review dates).
- Team members are free text (name and role), not linked user accounts. "Responsible staff" on
  goals is also free text.
- Progress monitoring against the review dates is a later stage.
- AUDIT LOGGING IS NOT DONE YET (Stage 14). Each version records who created and who finalized
  it. Edits to drafts are not logged.

STAGE 10 - ILAW ALIGNMENT
-------------------------------------------------------------------------------

Not yet confirmed or checked
- "ILAW" was not defined anywhere in the project. It was built as a DAILY LEARNING ACTIVITY LOG
  (decided with the developer on 2026-11-28). If the school means something else by ILAW, the
  entry fields need to change.
- Migration 0010 has NOT been run on the development database yet ("alembic upgrade head").
- The ILAW tab has not been clicked through in a browser.

Alignment
- Suggestions are similarity only, and a teacher always decides. Nothing is linked as
  "confirmed" without a person.
- Only the ACTIVE IEP is used: the finalized version for the learner's CURRENT school year.
  Without one, no entries can be logged (not even for past dates).
- In a quick real-model check, English activities ranked the right goal first (0.42 to 0.58
  similarity against at most 0.32 for the wrong goals). A Filipino activity also ranked the
  right goal first but scored 0.28, which is below ILAW_MIN_SCORE (0.35), so it got NO
  suggestion. Teachers writing in Filipino will often need to link goals by hand, or
  ILAW_MIN_SCORE can be lowered (for example to 0.25).
- Suggestions use only the title and description, not the learner's response or the notes.
- When an IEP amendment is finalized, existing entries keep pointing at the old version until
  someone re-suggests them (or adds or changes a link). Their confirmed links to old-version
  goals stay as history.
- If the text changes, editing an entry re-runs the suggestions. Confirmed and rejected links
  are kept even if they no longer fit the new text.

Duplicates
- The duplicate rule compares the TITLE only (after lower-casing and collapsing spaces), for
  the same learner and date. "Subtraction with counters" and "Subtraction using counters" count
  as different activities.

Other
- No photos or file attachments on entries.
- The activity date must be within the IEP period and not in the future.
- Entries can be edited and deleted by any writer (Coordinator or assigned Teacher), not only by
  the teacher who created them.
- Progress scoring per goal (using the confirmed links and the learner's response) is not built
  yet. ilaw_alignment_service.entries_for_goal() is ready for it.
- AUDIT LOGGING IS NOT DONE YET (Stage 14). Each link records who decided and when. Entry edits
  and deletions are not logged.

STAGE 11 - PROGRESS MONITORING
-------------------------------------------------------------------------------

Not yet confirmed or checked
- Migration 0011 has NOT been run on the development database yet ("alembic upgrade head").
- The chart (shared/charts/ProgressChart.jsx), the Progress tab, the timeline and Progress
  alerts have NOT been looked at in a browser. The chart's series colour passed the dataviz
  palette validator in light and dark mode, but layout details (label overlap near the right
  edge, tooltip position on small screens) still need a visual check. The app has no dark
  mode, so only the light colours are used.

Status rules (fixed; change progress_analysis.py if the school wants different ones)
- The aim line is a STRAIGHT line from the baseline (at the goal's start date) to the target
  (at the target date).
- A goal is "below aim line" when the MEDIAN OF THE LAST 3 POINTS is behind the line on the
  date of the latest point. One bad point alone does not flag a goal.
- "No recent data" = nothing recorded for more than 30 days. "No data yet" = no points at all,
  more than 30 days after the goal's start. Both windows are fixed at 30 days.
- The direction is INFERRED: if the target is lower than the baseline, it is treated as a
  "decrease" goal (lower is better). There is no separate setting.
- Goals without a numeric baseline value in the IEP get "No numeric baseline" and no aim line.
  The Stage 9 builder fills the baseline TEXT automatically, but staff must type the baseline
  VALUE.
- "Target met" looks at the latest point only (it does not require several points at
  target).
- Status is calculated on request, not stored, so the alert list reflects the data at the
  moment it is opened.

Data entry
- The value's unit always comes from the IEP goal. Percent goals also accept correct/total,
  which is saved as a percentage (the raw counts are not kept).
- Trials store successes and "out of". The chart plots successes (the goal targets are written
  that way, e.g. 4 of 5 trials).
- Grades (0-100) are never plotted on goal charts, because they use a different scale. They
  appear under the goal card and in the timeline.
- Dates must be inside the period of the IEP that was active when the record was made, and
  cannot be in the future.
- Records stay linked to the IEP version they were made under. After an amendment, the charts
  of the new version start without the old data points (the goals are new copies).
- There is no CSV export of progress data yet.
- AUDIT LOGGING IS NOT DONE YET (Stage 14). Records keep who created them, but edits and
  deletions are not logged.
